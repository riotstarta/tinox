Tinox

Eine kompilierte, objektorientierte Programmiersprache mit Java-ähnlicher Syntax, LLVM-Backend, integriertem HTTP-Server und vollständigem IDE-Tooling – entwickelt für performante Backend-Services.

Kompiliert LLVM Objektorientiert REST-API LSP High-Performance

Was ist Tinox?

Tinox ist eine eigenständig entwickelte, statisch typisierte Programmiersprache, die direkt zu nativen Maschinenbefehlen kompiliert wird. Die Sprache kombiniert eine Java-ähnliche, annotation-getriebene Syntax mit den Leistungsvorteilen eines LLVM-basierten Compilers und einem in C geschriebenen Laufzeitsystem.

Der Hauptfokus liegt auf der einfachen Entwicklung hochperformanter HTTP-REST-Dienste: Ein Controller-Handler benötigt nur wenige Zeilen Code, und der eingebaute HTTP-Server basiert auf epoll und SO_REUSEPORT – Technologien, die auch in produktionsreifen Webservern wie Nginx eingesetzt werden.

Kernidee: Die Produktivität eines frameworks wie Spring Boot oder Quarkus – ohne JVM-Overhead, Garbage-Collector-Pausen oder hohen Speicherverbrauch. 
import tinox.core.http_server;
import tinox.core.json;

class SortController
{
    @POST
    @Path("/sort")
    @Consumes(MediaType.APPLICATION_JSON)
    @Produces(MediaType.APPLICATION_JSON)
    fn sort(ctx: HttpContext) -> Nothing
    {
        let root: JsonValue = Json.parse(ctx.request.body);
        let numbers: List<Int64> = Json.intArrayFromJson(root.getField("numbers"));
        ctx.response.body = Json.intArrayWrap("sorted", numbers.sort());
    }
}

Dieser Code stellt einen vollständig funktionsfähigen REST-Endpunkt dar – kein Framework-Konfigurationsaufwand, keine XML-Dateien, kein Boilerplate.

Technische Grundlagen

LLVM als Compiler-Backend

Der Tinox-Compiler erzeugt keine nativen Maschinenbefehle direkt, sondern LLVM Intermediate Representation (LLVM IR) – eine plattformunabhängige, typisierte Assemblersprache. Das LLVM-Toolchain übernimmt dann die Optimierung und Übersetzung in Maschinencode.

Vorteil: Tinox profitiert automatisch von allen LLVM-Optimierungen (Loop-Unrolling, Inlining, Dead-Code-Elimination, Link-Time-Optimization) ohne eigene Optimierungslogik implementieren zu müssen.

LLVM wird auch von Clang (C/C++), Rust, Swift, Julia und Kotlin Native verwendet – es ist eines der ausgereiftesten Compiler-Backends der Industrie.

Rust als Implementierungssprache

Der gesamte Compiler – Lexer, Parser, Typchecker, Codegenerator und LSP-Server – ist in Rust implementiert. Das bringt folgende Vorteile:

  • Sicherheit Kein Undefined Behavior, keine Speicherfehler im Compiler selbst
  • Performance Schnelle Compile-Zeiten des Compilers (keine GC-Pausen)
  • Parallelität Thread-sichere Datenstrukturen (DashMap) für den LSP-Server

C als Laufzeitsystem

Das Laufzeitsystem (runtime.c) ist in C geschrieben und stellt alle Betriebssystem-nahen Funktionen bereit: Speicherverwaltung, Strings, Arrays, Maps, Datei-I/O, Netzwerk und den HTTP-Server. C-Funktionen werden direkt aus dem LLVM IR heraus aufgerufen – kein ABI-Overhead durch Wrapper-Schichten.

Wichtige Konzepte

🔤

Statische Typisierung

Alle Typen werden zur Compile-Zeit geprüft. Keine Laufzeit-Typfehler möglich.

🔗

AOT-Kompilierung

Ahead-of-Time: Der Quellcode wird vor der Ausführung vollständig zu einem nativen Binary kompiliert. Kein Interpreter, kein JIT.

♻️

Boehm GC

Tinox verwendet den Boehm Garbage Collector – einen konservativen, thread-sicheren GC. Speicher wird automatisch freigegeben; der Entwickler muss nichts manuell verwalten.

🧵

1:1 Threading

Jeder spawn-Aufruf erstellt einen echten OS-Thread (pthread). Volle Parallelität auf mehreren CPU-Kernen.

Compiler-Pipeline

Der Tinox-Compiler transformiert eine .tnx-Quelldatei in mehreren Schritten zu einem ausführbaren nativen Binary:

1

Lexer (tinox-lexer)

Liest den UTF-8-Quelltext und zerlegt ihn in Tokens (kleinste bedeutungsvolle Einheiten): Schlüsselwörter, Bezeichner, Literale, Operatoren, Klammern. Jedes Token trägt präzise Positionsinformationen (Zeile, Spalte, Byte-Offset) für spätere Fehlermeldungen. Unterstützt String-Interpolation ("Hallo ${name}!").

2

Parser (tinox-parser)

Wandelt die Token-Sequenz in einen Abstract Syntax Tree (AST) um – eine Baumstruktur, die die syntaktische Struktur des Programms darstellt. Rekursiver Abstieg-Parser: Jede Grammatikregel entspricht einer Funktion. Erkennt Klassen, Methoden, Ausdrücke, Schleifen, Match-Ausdrücke etc.

3

Import-Auflösung (tinox CLI)

import-Deklarationen werden rekursiv aufgelöst: Die importierten .tnx-Dateien (aus der Standardbibliothek oder dem Projektverzeichnis) werden geladen, geparst und in den AST eingebettet. Das Ergebnis ist ein einziger, zusammengefasster AST mit allen benötigten Deklarationen.

4

Typchecker (tinox-typecheck)

Zwei-Pass-Verfahren: Erst werden alle Deklarationen (Klassen, Methoden, Funktionen) registriert, dann werden Ausdrücke und Anweisungen auf Typkorrektheit geprüft. Validiert auch Annotationen (@GET, @POST, @Produces usw.), extrahiert REST-Routen und erkennt DI-Komponenten.

5

Code-Generator (tinox-codegen)

Traversiert den AST direkt und erzeugt LLVM IR als Text. Generiert Vtable-Strukturen für Interface-Dispatch, monomorphisiert generische Funktionen/Klassen, alloziert Closure-Environments, erzeugt HTTP-Route-Handler. Kein Zwischenschritt – direkt AST → IR.

6

llc (LLVM Compiler)

Das externe LLVM-Werkzeug llc übersetzt das LLVM IR in Assembler. Im Release-Modus mit -O3 werden umfangreiche Optimierungen (Inlining, Loop-Optimierungen, Vektorisierung) durchgeführt.

7

Clang (C Compiler / Linker)

clang kompiliert runtime.c zu einem Objekt-File und verknüpft es mit dem generierten Assembler zu einem fertigen nativen Binary. Dabei wird auch -lm (Mathe-Bibliothek) gelinkt.

Ergebnis: Ein einzelnes, statisch verlinktes Binary ohne externe Abhängigkeiten (außer der C-Standardbibliothek). Startzeit: <1ms.

Runtime (C-Laufzeitsystem)

Das Herzstück des Tinox-Laufzeitsystems ist runtime/runtime.c (~1.700 Zeilen C-Code). Es stellt alle Primitive bereit, auf die der generierte LLVM IR direkt zugreift.

Speicherverwaltung

Tinox verwendet den Boehm Garbage Collector (libgc) für automatisches Speichermanagement. Der GC ist konservativ: Er scannt Stack und Register nach Zeigern und gibt nicht mehr erreichbare Objekte frei – ohne dass der Entwickler explizit free() aufrufen muss. Durch GC_THREADS ist er vollständig thread-sicher und funktioniert korrekt mit dem epoll-basierten HTTP-Server-Thread-Pool.

Für häufige Operationen (Sort, JSON-Parsing) werden thread-lokale statische Puffer verwendet, die einmal alloziert und dann wiederverwendet werden – das eliminiert den malloc-Overhead im Request-kritischen Pfad komplett.

Async & Concurrency

Das Concurrency-Modell basiert auf POSIX-Threads (pthreads). spawn erstellt einen echten OS-Thread. Channels nutzen intern eine Linked-List-Queue mit Mutex und Condition Variable.

HTTP-Server (Low Level)

Der HTTP-Server im Runtime verwendet:

  • SO_REUSEPORT Mehrere Threads binden den gleichen Port – der Kernel verteilt Verbindungen
  • epoll Event-Multiplexing: ein Thread verwaltet bis zu 4.096 gleichzeitige Verbindungen
  • TCP_NODELAY Nagle-Algorithmus deaktiviert – sofortiges Senden kleiner Pakete
  • Keep-Alive HTTP/1.1 keep-alive, Idle-Timeout 500ms

LSP – Grundlagen

Das Language Server Protocol (LSP) ist ein von Microsoft im Jahr 2016 entwickeltes offenes Protokoll, das die Kommunikation zwischen einem Sprachserver (der die Programmiersprache versteht) und einem Editor (der die Benutzeroberfläche zeigt) standardisiert.

Das Problem vor LSP

Früher musste jede IDE für jede Sprache eigene Plugins implementieren: Eclipse-Plugin für Java, VS-Code-Plugin für Java, IntelliJ-Plugin für Java – alles separate Implementierungen der gleichen Logik. Bei n Sprachen und m Editoren entstanden n × m Integrationen.

LSP-Lösung: n + m statt n × m

Mit LSP schreibt man einmal einen Sprachserver, und jeder LSP-kompatible Editor nutzt ihn automatisch. Der Sprachserver kommuniziert über JSON-RPC über stdio mit dem Editor.

      ▼

      │
      │  Analysiert .tnx-Dateien
      ▼
Lex → Parse → Typecheck → Antworten an Editor

Tinox LSP-Server

tinox-lsp ist ein vollständiger LSP-Server, implementiert mit tower-lsp 0.20 (Rust) und Tokio als asynchronem Laufzeitsystem.

Eingebettete Standardbibliothek

Alle 26+ Standardbibliotheks-Module sind mittels include_str!() direkt in das LSP-Binary eingebettet. Der Server benötigt keine Installation oder Konfiguration von Dateipfaden – er funktioniert sofort nach dem Kopieren des Binaries.

Import-Auflösung für Diagnostics

Wenn eine .tnx-Datei geöffnet wird, löst der LSP-Server automatisch import-Deklarationen auf und lädt die entsprechenden Stdlib-ASTs als Prelude. So werden Json.parse() oder HttpContext nicht als "undefined" markiert.

Dot-Completion für Klassen

Wenn der Nutzer Json. tippt:

  1. Der Editor schickt textDocument/completion mit dem Offset nach dem Punkt
  2. Der LSP extrahiert die Dot-Chain (["Json"])
  3. Er prüft, ob Json eine Variable (Instanz) oder ein Klassenname ist
  4. Falls Klassenname: direkt die Methoden von Json aus der Registry laden
  5. Statische Methoden (fnc) werden mit dem Hinweis fnc parse(...) angezeigt

HTTP-Server & Performance

Der integrierte HTTP-Server ist auf maximale Durchsatzrate bei minimaler Latenz optimiert. Er verwendet Technologien, die auch in produktionsreifen Systemen wie Nginx und Envoy eingesetzt werden.

epoll – Event-Multiplexing

Statt für jede Verbindung einen Thread zu blockieren, registriert der Server alle aktiven Verbindungen in einem epoll-Dateideskriptor. Ein epoll_wait()-Aufruf liefert alle Verbindungen, die lesebereite Daten haben – in einem einzigen Systemaufruf. 

// Konzept (vereinfacht):
epoll_fd = epoll_create1(0);
// Alle aktiven Verbindungen registrieren...
while (true)
{
    events = epoll_wait(epoll_fd, max_events, 50); // 50ms Timeout
    for event in events
    {
        if event.fd == server_socket { accept(); }
        else { handle_request(event.fd); }
    }
}

SO_REUSEPORT – Kernel Load Balancing

Mit SO_REUSEPORT können mehrere Threads (oder Prozesse) gleichzeitig auf demselben Port lauschen. Der Linux-Kernel verteilt eingehende Verbindungen automatisch auf die verfügbaren Listener – ohne Locks, ohne Engpässe.

Thread-lokale Puffer

Jeder HTTP-Worker-Thread hat seinen eigenen statischen Puffer für Request-Daten, Response-Daten und JSON-Parsing. Diese Puffer werden nie freigegeben und wiederverwendet – das eliminiert malloc/free im kritischen Request-Pfad vollständig.

Ergebnis: Bis zu 4.096 gleichzeitige Verbindungen pro Thread, lineares Skalieren über CPU-Kerne durch SO_REUSEPORT.

http3_server

import tinox.core.http3_server;

HTTP/3 (RFC 9114) über QUIC (RFC 9000). Anders als http_server (Protokoll komplett in C) und http2_server (Framing/HPACK in reinem Tinox) kann dieses Modul die Protokolllogik nicht nach Tinox verlagern: QUIC-Transport (Verlusterkennung, Congestion Control, AEAD) und HTTP/3-Framing + QPACK laufen in den C-Bibliotheken ngtcp2 und nghttp3, deren Callback-basierte C-APIs nicht mitten in einem Callback in einen Tinox-Closure zurückrufen können. Der gesamte QUIC/HTTP-3/QPACK-Zustand lebt daher in runtime.c hinter opaken Int64-Handles (dasselbe Muster wie die bestehende TLS-Conn-Architektur) — diese Datei registriert nur Routen und pumpt die native Event-Loop, verwendet aber dieselbe Route/RouteMatcher/HttpRequest/ HttpResponse/HttpContext-API wie http_server/http2_server unverändert weiter.

TLS ist Pflicht (QUIC kennt keinen Klartext-Modus) — Zertifikat/Key gehen direkt an den Konstruktor, es gibt kein separates listen()/ listenTls() wie bei HttpServer.

Build-Flag: erfordert einen mit TINOX_HTTP3=1 gebauten Compiler-Lauf (Opt-in, standardmäßig AUS — anders als TINOX_TLS, das standardmäßig AN ist: OpenSSL ist praktisch überall vorhanden, ngtcp2/nghttp3 deutlich seltener; ein Default-AN würde tinox build auf jedem System ohne diese Bibliotheken mit einem Compile-Fehler brechen statt mit einer sauberen Laufzeit-Meldung). Setzt außerdem voraus, dass TLS aktiviert ist (ngtcp2_crypto_ossl braucht OpenSSL).

Bekannte Einschränkung (0-RTT): enableEarlyData(), HttpRequest.wasEarlyData und die 425-Too-Early-Policy für nicht-idempotente Early-Data-Requests sind vollständig verdrahtet, aber SSL_CTX_set_max_early_data selbst ist unter der hier verwendeten Kombination aus OpenSSL 3.6.3 + ngtcp2_crypto_ossl 1.25.0 bewusst NICHT gesetzt (das Setzen führte in Tests reproduzierbar zu einem Hänger direkt nach Abschluss des TLS-Handshakes, Root Cause im verfügbaren Zeitrahmen nicht isoliert). Dadurch akzeptiert die TLS-Schicht nie tatsächlich 0-RTT-Daten — ein Client, der Early Data versucht, fällt transparent auf einen normalen 1-RTT-Roundtrip zurück; wasEarlyData ist also aktuell immer false. Kein Absturz, nur ein noch nicht aktives Feature.

@Http3RestController — deklarativ statt fluent API

Dieselben @GET/@POST/@PUT/ @PATCH/@DELETE/@Path/ @StatusCode/@Produces/@Consumes/ @Auth/@OIDCRolesAllowed-Annotationen wie beim normalen (TCP-)REST-Auto-Server (Modul rest) funktionieren auch für HTTP/3 — mit der zusätzlichen Klassen-Annotation @Http3RestController(port, certPath, keyPath) generiert der Compiler einen kompletten Http3Server::new()/ .get()/.post()/…/.listen()-`main`, exakt wie ihn die handgeschriebene Fluent-API-Variante oben schreiben würde — nicht über den GC-Crash-anfälligen TCP-Auto-Server (tinox_HttpServer_listen, Issue #140), sondern direkt auf Http3Server.

Höchstens eine @Http3RestController-Klasse pro Programm (hart erzwungen); alle @GET/… Routen im gesamten Programm landen auf diesem einen Server. Nicht kombinierbar mit @WebsocketEndpoint/@Amqp10Consumer/ @Amqp091Consumer (jede erzeugt ihr eigenes Auto-`main`). Da der Compiler pro Request standardmäßig eine frische, genullte Controller-Instanz alloziert, braucht ein Controller mit Zustand zusätzlich @ApplicationComponent (eine wiederverwendete Singleton-Instanz über {Klasse}_di_get()) — Beispiel und Details dazu in examples/http3_rest_api/src/TaskController.tnx. 

import tinox.core.http3_server;

@Http3RestController(8843, "cert.pem", "key.pem")
class TaskController
{
    var tasks: List<Task>;

    @GET
    @Path("/tasks")
    fn listTasks(ctx: HttpContext) -> Nothing
    {
        ctx.response.json(Json::serialize(this.tasks));
    }
}

Ws::sendBinaryfn sendBinary(conn: Int64, bytes: List<Int64>) -> NothingSendet einen Binary-Frame (Opcode 2), ein Byte pro Listen-Slot.
Ws::sendPingfn sendPing(conn: Int64) -> NothingSendet einen Ping-Frame.
Ws::sendClosefn sendClose(conn: Int64, code: Int64) -> NothingSendet einen Close-Frame mit dem angegebenen Statuscode.
Ws::closefn close(conn: Int64) -> NothingSchließt die zugrunde liegende Verbindung.
Ws::textfn text(f: WsFrame) -> StringWandelt den Payload eines Frames in einen String um (byte-basiert).
WsFrame{ fin: Bool, opcode: Int64, payload: List<Int64>, rsv1: Bool }Ein gelesener Frame. Opcode wie RFC 6455 (1 Text, 2 Binary, 8 Close, 9 Ping, 10 Pong); zusätzlich -1 = Verbindung zu/EOF, -2 = Protokollfehler (Verbindung wurde bereits mit Close beantwortet). rsv1 ist nur intern relevant (permessage-deflate-Reassemblierung) — payload ist von readMessage bereits dekomprimiert.

Beispiel

import tinox.core.websocket;

let srv: Int64 = WsServer::listen(8790);

while true {
    let conn: Int64 = WsServer::accept(srv);
    if conn <= 0 { continue; }

    while true {
        let f: WsFrame = Ws::readMessage(conn);
        if f.opcode == 1 {
            Ws::sendText(conn, "echo: " + Ws::text(f));
            continue;
        }
        if f.opcode == 2 {
            Ws::sendBinary(conn, f.payload);
            continue;
        }
        break; // Close (8), EOF (-1) oder Protokollfehler (-2)
    }
    Ws::close(conn);
}

Bewusste v1-Lücken: Payload-Cap 16 MB (gilt auch für zusammengesetzte fragmentierte Nachrichten, s. u., und für den dekomprimierten permessage-deflate-Output, s. u.). wss:// (TLS) wird unterstützt, s. listenTls/acceptTls oben. Fragmentierte Nachrichten (Continuation-Frames, §5.4) werden von readMessage transparent zusammengesetzt; ausgehende Verbindungen als Client deckt WsClient ab, s. u. — WsClient bietet permessage-deflate v1 bewusst nicht an (s. permessage-deflate-Abschnitt unten).

permessage-deflate (RFC 7692)

Bietet ein Client Sec-WebSocket-Extensions: permessage-deflate im Handshake-Request an, nimmt Ws::handshake (und damit WsServer::accept/acceptTls) das immer mit client_no_context_takeover; server_no_context_takeover an (RFC 7692 §7.1.1 erlaubt dem Server, diese Parameter unilateral in seine Response zu setzen) — jede Nachricht bekommt dadurch einen frischen DEFLATE-Kontext, es gibt keinen persistenten Kompressions-Zustand pro Verbindung zu verwalten oder beim Schließen freizugeben. Für Aufrufer komplett transparent: readMessage liefert bereits dekomprimierten Payload, sendText/sendBinary komprimieren automatisch, wenn die Verbindung die Extension ausgehandelt hat — keine API-Änderung nötig, kein separates *Compressed- Gegenstück. Bietet der Client die Extension nicht an, verhält sich die Verbindung exakt wie vor diesem Feature (keine Kompression).

WsClient (ausgehende Verbindungen) bietet die Extension v1 bewusst nicht an — ein echter Drittanbieter-Server könnte mit Context- Takeover (dem RFC-7692-Default) antworten, was persistenten Kompressions- Zustand über mehrere Nachrichten hinweg erfordern würde; das ist der gleiche architektonische Zielkonflikt, der ursprünglich gegen permessage-deflate in diesem Modul sprach, nur aus der Client- statt der Server-Perspektive.

wss:// (TLS)

listenTls/acceptTls ersetzen listen/accept 1:1 — der restliche Code (Handshake, readMessage, sendText etc.) bleibt unverändert, weil die zugrunde liegenden Conn-Handle-Primitiven schon transparent für TLS- und Plaintext-Verbindungen sind: 

import tinox.core.websocket;

let srv = WsServer::listenTls(8791, "cert.pem", "key.pem");
if srv < 0 { return 1; } // Port belegt, TINOX_TLS=0 gebaut, oder Cert/Key ungueltig

let conn = WsServer::acceptTls(srv); // TLS- + WS-Handshake

OpenSSL ist standardmäßig gelinkt, genau wie bei HttpServer::listenTls — kein Extra-Flag nötig. Opt-out per TINOX_TLS=0, falls kein OpenSSL zum Bauen verfügbar ist.

amqps:// (TLS)

connectTls ersetzt connect 1:1 — der restliche Code bleibt unverändert, weil der komplette Handshake über dieselben TLS-/Plaintext-transparenten Conn-Primitiven läuft: 

let conn = AmqpConnection091::connectTls("broker.example.com", 5671, "/", "guest", "guest", true);
// verify=true prueft Zertifikatskette + Hostname gegen System-CA-Stores;
// verify=false ist ein bewusster Opt-out fuer selbstsignierte Testzertifikate.

OpenSSL ist standardmäßig gelinkt, genau wie bei HttpServer::listenTls/WsServer::listenTls — kein Extra-Flag nötig. Opt-out per TINOX_TLS=0, falls kein OpenSSL zum Bauen verfügbar ist.

Heartbeats (§4.2.7) laufen wie bei amqp10 auf einem Hintergrund-Thread, explizites Opt-in: conn.heartbeat ist das vom Broker in connection.tune vorgeschlagene Intervall in Sekunden (rein informativ, bis startHeartbeat aufgerufen wird). 

conn.startHeartbeat(20000);   // alle 20s ein Heartbeat-Frame, im Hintergrund
// ...
conn.stopHeartbeat();         // oder einfach conn.close(), das stoppt ihn mit

Bewusste v1-Lücken: keine Transaktionen (tx.select), kein Auto-Reconnect, kein eigener CA-Bundle-Parameter bei connectTls (verifiziert nur gegen die System-CA-Stores). AMQP 1.0 ist nicht Teil dieses Moduls.

Mehrere Channels

AmqpChannel091::open kann beliebig oft auf derselben AmqpConnection091 aufgerufen werden — jeder Aufruf bekommt eine eigene, fortlaufend vergebene Channel-ID und eine eigene Frame-Inbox. Ein Hintergrund-Task pro Connection liest jeden Frame vom Socket und routet ihn per Channel-ID an die richtige Inbox, sodass ein Channel mit unabhängigem Traffic (z. B. ein laufender Consumer) einen anderen Channel, der gerade synchron auf seine eigene Antwort wartet (declareQueue/qos/consume/...), nicht stört: 

let conn = AmqpConnection091::connect("127.0.0.1", 5672, "/", "guest", "guest");
let ch1 = AmqpChannel091::open(conn);   // Channel-ID 1
let ch2 = AmqpChannel091::open(conn);   // Channel-ID 2, unabhaengig von ch1

Innerhalb EINES Channels bleibt die v1-Einschränkung bestehen, dass nicht nach Methodentyp dispatcht wird — z. B. gleichzeitig auf demselben Channel zu konsumieren UND auf Publisher-Confirms zu warten ist weiterhin unsicher (waitForConfirm könnte ein basic.deliver fälschlich als Confirm lesen). Für diesen Fall getrennte Channels verwenden.

Publisher-Confirms

let selected = ch.confirmSelect();
let tag = ch.publish("amq.direct", "rk", body, "text/plain"); // tag == 1, 2, 3, ...
let confirm = ch.waitForConfirm();
if confirm.ok {
    if confirm.ack {
        // Broker hat die Nachricht mit Tag confirm.deliveryTag angenommen
    } else {
        // basic.nack -- Broker konnte sie nicht verarbeiten, ggf. neu senden
    }
}

Annotationsgesteuertes REST-Framework für den Aufbau von HTTP-APIs mit deklarativem Routing. Controller-Klassen werden mit Annotationen wie @Path, @GET, @POST, @Produces, @Consumes, @StatusCode, @Auth und @OIDCRolesAllowed deklariert und dann bei RestApi registriert (oder — bei rein annotationsbasierten Controllern ohne explizite RestApi-Verdrahtung — vom Compiler direkt zu Routen-Dispatch-Code übersetzt, inkl. eines automatisch generierten main(), falls keines vorhanden ist). Das Framework unterstützt globale Middleware, CORS, automatische Content-Type-Verwaltung und Dependency-Injection-Annotationen (@ApplicationComponent, @Inject, @Startup, @HttpRequestScoped).

@Auth("bearer")/@Auth("basic") validiert seit issue #141 wirklich das Credential statt nur das Schema- Prefix des Authorization-Headers zu prüfen (vorher akzeptierte jedes syntaktisch passende "Bearer ..."/"Basic ..." jeden beliebigen Wert). Für Controller, die über die RestApi-Klasse registriert werden, war das bereits über RestApi::setAuthValidator möglich; für rein annotationsbasierte Controller (kompilierte Routen ohne RestApi-Instanz) sucht der Compiler jetzt nach einer projekteigenen Klasse AuthValidator mit fnc validate(authType: String, credential: String) -> Bool und ruft sie auf, wenn vorhanden — ohne eine solche Klasse wird jede @Auth-geschützte Anfrage abgelehnt (sicherer Standard statt stillschweigend offen, analog zu RestApi::authValidators eigenem Standardverhalten).

@OIDCRolesAllowed(["rolle1", "rolle2"]) (issue #142) verlangt einen verifizierten OIDC-Access-Token mit mindestens einer der angegebenen Realm-Rollen — vollständig deklarativ, ohne dass der Handler selbst irgendetwas davon merkt. Die Verifikation (RS256-Signatur über das JWKS des IdP, iss/aud/ exp/nbf, Rollen-Abgleich gegen realm_access.roles) läuft automatisch über OidcGuard::checkRoles; die IdP-Anbindung selbst (OIDC_ISSUER/OIDC_JWKS_URI/OIDC_AUDIENCE) kommt aus Umgebungsvariablen, sodass dieselbe kompilierte Anwendung ohne Neubau gegen jeden RS256/JWKS-fähigen IdP läuft — siehe examples/keycloak_oidc_api für ein vollständiges Beispiel mit echtem Keycloak via docker-compose. Bekanntes Problem (issue #140): der vom Compiler für annotationsbasierte Routen automatisch generierte, epoll-/Thread-Pool- basierte Server (tinox_HttpServer_listen in runtime.c — ein anderer, mehrfädiger Server als die unten dokumentierte einfädige HttpServer-Klasse) kann nach wenigen Anfragen an jede allokationsintensive Route innerhalb des Boehm-GC abstürzen (kein @OIDCRolesAllowed-spezifisches Problem — reproduzierbar auch mit einer trivialen Route ohne jede Kryptografie/JSON/Netzwerk-Beteiligung). Leichte, interaktive Nutzung funktioniert zuverlässig; die Klasse HttpServer selbst ist nicht betroffen.

import tinox.core.jwt;

JSON Web Token (JWT) Implementierung mit HMAC-SHA256- (HS256) und seit issue #138 auch RSASSA-PKCS1-v1_5-SHA256-Signierung (RS256, gegen einen per Jwks geholten Provider-Schlüssel). oauth2

import tinox.core.oauth2;

OAuth2-Client für den Authorization-Code-Grant mit PKCE (RFC 6749 + RFC 7636) — der empfohlene Flow für Server- und Public-Clients gegen Drittanbieter-Provider (Google, GitHub, …). OAuth2Client kapselt den kompletten Ablauf: Authorize-URL bauen (inkl. sicherem state für CSRF-Schutz und PKCE-code_challenge), den Callback-Code gegen ein Token-Paar tauschen, und Tokens erneuern. Der zugrundeliegende http-Client unterstützt seit diesem Modul auch https:// (strikte Zertifikatsprüfung), sodass echte Provider-Endpunkte direkt angesprochen werden können.

Bewusste v1-Lücken: nur Authorization Code + PKCE (kein client_credentials/implicit/ device_code), kein Token-Storage — das bleibt wie beim restlichen rest/http_server-Framework Aufrufer-Sache. Für „Login mit X" inkl. verifiziertem OIDC-ID-Token (Signatur, iss/aud) siehe das Modul oidc (OidcClient, issue #138), das auf diesem Client aufbaut.

import tinox.core.oauth2;

fn main() -> Nothing
{
    let client: OAuth2Client = OAuth2Client::new(
        "https://accounts.google.com/o/oauth2/v2/auth",
        "https://oauth2.googleapis.com/token",
        "meine-client-id",
        "mein-client-secret",
        "https://meine-app.example.com/callback"
    );

    // 1. Nutzer zur Provider-Login-Seite weiterleiten
    let authReq: OAuth2AuthorizeRequest = client.buildAuthorizeUrl("openid email");
    // authReq.state und authReq.codeVerifier session-seitig speichern,
    // dann den Browser zu authReq.url weiterleiten.
    println("Weiterleiten zu: " + authReq.url);

    // 2. Im Callback-Handler: state gegen den gespeicherten Wert prüfen,
    //    dann den Code gegen ein Token-Paar tauschen.
    let tokens: OAuth2TokenResponse = client.exchangeCode("code-aus-dem-callback", authReq.codeVerifier);
    if tokens.ok {
        println("Access-Token: " + tokens.accessToken);
    } else {
        println("Fehler: " + tokens.errorMessage);
    }

    // 3. Später: Token erneuern
    let refreshed: OAuth2TokenResponse = client.refresh(tokens.refreshToken);
    if refreshed.ok {
        println("Neues Access-Token: " + refreshed.accessToken);
    }
}

import tinox.core.oidc;

„Login mit X" (OpenID Connect) auf Basis von OAuth2Client (Modul oauth2): OidcClient führt denselben Authorization-Code+PKCE-Flow aus, verifiziert aber zusätzlich das vom Provider gelieferte id_token — RS256-Signatur gegen den per Jwks geholten Provider-Schlüssel (Modul jwt), sowie iss/aud/exp/ nbf — statt es ungeprüft zu übernehmen, und liefert die verifizierten Claims (sub, email, …) zurück (issue #138).

Bewusste v1-Lücken: kein JWKS-Caching (jede Verifikation holt das JWKS-Dokument frisch — ein Caching-Layer ist separate Folgearbeit, falls das zum echten Kostenfaktor wird), nur Authorization Code + PKCE (kein client_credentials/ implicit/device_code), kein Token-Storage — gleiche Haltung wie bei oauth2.

OidcClient::buildAuthorizeUrl fn buildAuthorizeUrl(scope: String) -> OAuth2AuthorizeRequest Wie OAuth2Client::buildAuthorizeUrl, prüft aber zuerst, dass scope "openid" enthält — sonst kommt vom Provider gar kein id_token zurück, was sonst erst bei exchangeCode als verwirrender Fehler sichtbar würde. import tinox.core.oidc;

fn main() -> Nothing
{
    let client: OidcClient = OidcClient::new(
        "https://accounts.google.com",
        "https://accounts.google.com/o/oauth2/v2/auth",
        "https://oauth2.googleapis.com/token",
        "https://www.googleapis.com/oauth2/v3/certs",
        "meine-client-id",
        "mein-client-secret",
        "https://meine-app.example.com/callback"
    );

    // 1. Nutzer zur Provider-Login-Seite weiterleiten ("openid" ist Pflicht)
    let authReq: OAuth2AuthorizeRequest = client.buildAuthorizeUrl("openid email");
    println("Weiterleiten zu: " + authReq.url);

    // 2. Im Callback-Handler: state prüfen, dann Code tauschen + id_token verifizieren
    let tokens: OidcTokenResponse = client.exchangeCode("code-aus-dem-callback", authReq.codeVerifier);
    if tokens.ok {
        println("Angemeldet als: " + tokens.claims["sub"].getString());
    } else {
        println("Fehler: " + tokens.errorMessage);
    }
}

OidcWebApp — fertiger Browser-Login "out of the box"

OidcClient oben ist der Low-Level-Baustein — der Aufrufer muss state/codeVerifier selbst zwischenspeichern und eine Session verwalten. OidcWebApp übernimmt genau das für den klassischen "besuche eine Seite, werde zu Keycloak/Google/… umgeleitet, komme eingeloggt zurück"-Fall (Spring Securitys "OAuth2 Login", Quarkus' application-type=web-app): install(server) registriert /login (leitet zum Provider um) und /callback (tauscht den Code, verifiziert das id_token, startet die Session) auf einem tinox.core.http_server.HttpServer — bewusst NICHT auf dem Annotation-gesteuerten Auto-Server, der unter allokationsintensiven Routen abstürzen kann (Issue #140), was dieser Flow (JSON, JWKS-Fetch, AES) durchgängig ist. Es gibt keinen serverseitigen Session-Speicher: sowohl der kurzlebige "Pending Login"-Zustand (PKCE-Verifier + CSRF-State, zwischen /login und /callback) als auch die Session selbst (die verifizierten Claims) leben komplett in httpOnly-Cookies, AES-256-GCM-versiegelt (Crypto::aesEncrypt/aesDecrypt) mit einem selbst gewählten Secret — ein manipuliertes Cookie oder ein falsches Secret lässt aesDecrypt werfen, das Cookie wird also verworfen statt akzeptiert. Dadurch überleben Sessions einen Server-Neustart und funktionieren über mehrere Prozesse hinweg ohne gemeinsamen Zustand.

Klasse / MethodeSignaturBeschreibung
OidcWebApp::new fn new(client: OidcClient, cookieSecret: String) -> OidcWebApp Wirft, wenn cookieSecret leer ist (ein leeres Secret ist ein bekannter, erratbarer Schlüssel, keine "Verschlüsselung aus").
OidcWebApp::install fn install(server: HttpServer) -> Nothing Registriert /login und /callback (Pfade konfigurierbar über loginPath/callbackPath) auf server. Einmal beim Start aufrufen, vor server.listen().
OidcWebApp::requireLogin fn requireLogin(ctx: HttpContext) -> Bool Session-Gate für eine Route: bei fehlendem/manipuliertem/abgelaufenem Session-Cookie wird zu loginPath umgeleitet und false zurückgegeben (Aufrufer muss sofort return;en), sonst true.
OidcWebApp::currentUser fn currentUser(ctx: HttpContext) -> Map<String, JsonValue> Die verifizierten Claims der aktuellen Session — sinnvoll direkt nach einem erfolgreichen requireLogin in derselben Anfrage.
OidcWebApp::logout fn logout(ctx: HttpContext) -> Nothing Löscht das Session-Cookie und leitet zu loginPath um.

Beispiel

import tinox.core.oidc;
import tinox.core.http_server;

fn main() -> Nothing
{
    let client: OidcClient = OidcClient::new(
        issuer, authorizeUrl, tokenUrl, jwksUri, clientId, clientSecret, redirectUri
    );
    let app: OidcWebApp = OidcWebApp::new(client, cookieSecret);

    let server: HttpServer = HttpServer::new(8096);
    app.install(server);

    server.get("/", ctx => {
        if !app.requireLogin(ctx) { return; }
        let claims: Map<String, JsonValue> = app.currentUser(ctx);
        ctx.response.text("Hallo, " + claims["sub"].getString());
    });

    server.get("/logout", ctx => { app.logout(ctx); });

    server.listen();
}

import tinox.core.base64;

fn main() -> Nothing
{
    // Einfacher String-Runden-Trip
    let original: String = "Hallo Tinox!";
    let kodiert: String = Base64::encode(original);
    println("Kodiert:   " + kodiert);

    let dekodiert: String = Base64::decode(kodiert);
    println("Dekodiert: " + dekodiert);

    // Byte-Liste kodieren
    let bytes: List<Int64> = [72, 101, 108, 108, 111];  // "Hello"

    {
        let n: Int64 = it.next(); // 0, 2, 4, 6, 8
    }

    // map: Quadratzahlen
    let zahlen: List<Int64> = [1, 2, 3, 4, 5];
    let quadrate: List<Int64> = Iter::map<Int64, Int64>(zahlen, fnc(x: Int64) -> Int64 { return x * x; });
    // [1, 4, 9, 16, 25]

    // filter: nur gerade Zahlen
    let gerade: List<Int64> = Iter::filter<Int64>(zahlen, fnc(x: Int64) -> Bool { return x % 2 == 0; });
    // [2, 4]

    // reduce: Summe
    let summe: Int64 = Iter::reduce<Int64, Int64>(zahlen, 0, fnc(acc: Int64, x: Int64) -> Int64 { return acc + x; });
    // 15

    // enumerate
    let paare: List<Pair<Int64, Int64>> = Iter::enumerate<Int64>(zahlen);
    // [(0,1),(1,2),(2,3),(3,4),(4,5)]

Das Modul zip ermöglicht das Erstellen, Öffnen und Bearbeiten von ZIP-Archiven. Dateien können hinzugefügt, extrahiert und entfernt werden. Einträge werden über ZipEntry-Objekte mit Name und Größe beschrieben; das Archiv selbst wird durch ZipArchive repräsentiert.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Zip::open fn open(path: String) -> ZipArchive Öffnet ein bestehendes ZIP-Archiv und liest seine Einträge.
Zip::create fn create(path: String) -> ZipArchive Erstellt ein neues, leeres ZIP-Archiv am angegebenen Pfad.
Zip::listEntries fn listEntries(path: String) -> List<ZipEntry> Gibt alle Einträge eines Archivs als Liste von ZipEntry-Objekten zurück.
Zip::extractFile fn extractFile(archive: ZipArchive, entryName: String) -> String Extrahiert den Inhalt eines Archiveintrags als Zeichenkette.
Zip::addFile fn addFile(archive: ZipArchive, name: String, content: String) -> Nothing Fügt dem Archiv eine neue Datei mit dem angegebenen Namen und Inhalt hinzu.
Zip::removeFile fn removeFile(archive: ZipArchive, entryName: String) -> Nothing Entfernt einen Eintrag aus dem Archiv.
Zip::close fn close(archive: ZipArchive) -> Nothing Schließt das Archiv (Abschlussoperation nach Bearbeitung).
ZipArchive path: String; entries: List<ZipEntry> Datenstruktur: Repräsentiert ein ZIP-Archiv mit Pfad und Eintrags-Liste.
ZipEntry name: String; size: Int64 Datenstruktur: Beschreibt einen einzelnen Archiveintrag mit Name und Größe in Bytes.

Beispiel

import tinox.core.zip;

// Neues Archiv erstellen und Dateien hinzufügen
let archiv: ZipArchive = Zip::create("/tmp/paket.zip");
Zip::addFile(archiv, "README.txt",  "Dies ist eine Tinox-Demo.\n");
Zip::addFile(archiv, "daten.csv",   "name,wert\nalpha,1\nbeta,2\n");
Zip::addFile(archiv, "config.json", "{\"version\": 1}\n");

// Einträge auflisten
let eintraege: List<ZipEntry> = archiv.entries;
var i: Int64 = 0;
while i < eintraege.len()
{
    let e: ZipEntry = eintraege[i];
    print(e.name + "  (" + e.size.toString() + " Bytes)\n");
    i = i + 1;
}

// Inhalt einer Datei extrahieren
let inhalt: String = Zip::extractFile(archiv, "README.txt");
print("README: " + inhalt);

// Eintrag entfernen
Zip::removeFile(archiv, "config.json");
print("Einträge nach Löschen: " + archiv.entries.len().toString() + "\n");

Zip::close(archiv);

asm

import tinox.core.asm;

Das Modul asm stellt einen einfachen Bytecode-Assembler bereit. Über die Klasse Assembler werden Opcodes und 64-Bit-Integer-Werte in einen Bytepuffer geschrieben, Labels gesetzt und aufgelöst sowie der fertige Bytecode als Byte-String exportiert. Die Klasse Ops definiert alle verfügbaren Opcodes als Integer-Konstanten.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung

Assembler::emit fn emit(asm: Assembler, op: Int64) -> Nothing Hängt ein einzelnes Byte (Opcode) an den Bytecode an.
Assembler::emitInt fn emitInt(asm: Assembler, value: Int64) -> Nothing Schreibt einen 64-Bit-Integer-Wert Little-Endian (8 Bytes) in den Bytecode.
Assembler::emitLabel fn emitLabel(asm: Assembler, name: String) -> Nothing Registriert ein Label an der aktuellen Bytecode-Position.
Assembler::resolveLabels fn resolveLabels(asm: Assembler) -> List<Int64> Gibt den aktuellen Bytecode (nach Label-Auflösung) als Integer-Liste zurück.
Assembler::toBytes fn toBytes(asm: Assembler) -> String Konvertiert den Bytecode in eine rohe Byte-Zeichenkette (ein Zeichen pro Byte).
Ops::Nop fn Nop() -> Int64 Opcode 0 – Keine Operation.
Ops::Halt fn Halt() -> Int64 Opcode 1 – Programm anhalten.
Ops::Load fn Load() -> Int64 Opcode 2 – Wert aus Speicher laden.
Ops::Store fn Store() -> Int64 Opcode 3 – Wert in Speicher schreiben.
Ops::Push fn Push() -> Int64 Opcode 4 – Wert auf Stack legen.
Ops::Pop fn Pop() -> Int64 Opcode 5 – Wert vom Stack nehmen.
Ops::Add fn Add() -> Int64 Opcode 6 – Addition.

Ops::Div fn Div() -> Int64 Opcode 9 – Division.
Ops::Jmp fn Jmp() -> Int64 Opcode 10 – Unbedingter Sprung.

Ops::Jnz fn Jnz() -> Int64 Opcode 12 – Sprung wenn Nicht-Null.

Beispiel

import tinox.core.asm;

// Assembler erstellen
let a: Assembler = Assembler::new();

// Einfaches Programm: lade 7, lade 3, addiere, halt
Assembler::emit(a, Ops::Push());
Assembler::emitInt(a, 7);

Assembler::emit(a, Ops::Push());
Assembler::emitInt(a, 3);

Assembler::emitLabel(a, "add_start");
Assembler::emit(a, Ops::Add());

// Bedingter Sprung zurück zur Schleife (Demo)
Assembler::emit(a, Ops::Jz());
Assembler::emitInt(a, 0);

Assembler::emit(a, Ops::Halt());

// Labels auflesen
let code: List<Int64> = Assembler::resolveLabels(a);
print("Bytecode-Länge: " + code.len().toString() + " Bytes\n");

// Als Byte-String exportieren
let bytes: String = Assembler::toBytes(a);
print("Rohdaten-Länge: " + bytes.len().toString() + "\n");

bitmap

import tinox.core.bitmap;

Das Modul bitmap stellt eine einfache 2D-Pixelgrafik-Bibliothek bereit. Bitmaps werden als Raster aus 32-Bit-Farbwerten (ARGB/RGB als Int64) verwaltet. Unterstützt werden das Erstellen, das pixelweise Lesen und Schreiben, das Füllen von Rechtecken sowie das Zeichnen von Linien und Kreisen (Bresenham-Algorithmen).

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Bitmap::create fn create(width: Int64, height: Int64, color: Int64) -> Bitmap Erstellt eine neue Bitmap mit den angegebenen Abmessungen, alle Pixel in color.
Bitmap::getPixel fn getPixel(bitmap: Bitmap, x: Int64, y: Int64) -> Int64 Gibt den Farbwert des Pixels an Position (x, y) zurück; außerhalb der Grenzen: 0.
Bitmap::setPixel fn setPixel(bitmap: Bitmap, x: Int64, y: Int64, color: Int64) -> Nothing Setzt das Pixel an (x, y) auf color; außerhalb der Grenzen: kein Effekt.
Bitmap::fillRect fn fillRect(bitmap: Bitmap, x: Int64, y: Int64, w: Int64, h: Int64, color: Int64) -> Nothing Füllt ein Rechteck beginnend bei (x, y) mit Breite w und Höhe h in color.
Bitmap::drawLine fn drawLine(bitmap: Bitmap, x0: Int64, y0: Int64, x1: Int64, y1: Int64, color: Int64) -> Nothing Zeichnet eine Linie von (x0, y0) nach (x1, y1) mithilfe des Bresenham-Algorithmus.
Bitmap::drawCircle fn drawCircle(bitmap: Bitmap, cx: Int64, cy: Int64, radius: Int64, color: Int64) -> Nothing Zeichnet einen Kreis mit Mittelpunkt (cx, cy) und dem angegebenen Radius (Midpoint-Algorithmus).

Beispiel

import tinox.core.bitmap;

// Farben als ARGB-Hex-Werte
let weiss: Int64  = 0xFFFFFFFF;
let schwarz: Int64 = 0xFF000000;
let rot: Int64    = 0xFFFF0000;
let blau: Int64   = 0xFF0000FF;

// 200×200 Pixel große weiße Bitmap erzeugen
let bild: Bitmap = Bitmap::create(200, 200, weiss);

// Schwarzen Rahmen zeichnen (vier Linien)
Bitmap::drawLine(bild,   0,   0, 199,   0, schwarz);
Bitmap::drawLine(bild, 199,   0, 199, 199, schwarz);
Bitmap::drawLine(bild, 199, 199,   0, 199, schwarz);
Bitmap::drawLine(bild,   0, 199,   0,   0, schwarz);

// Rotes gefülltes Rechteck in der Mitte
Bitmap::fillRect(bild, 50, 50, 100, 100, rot);

// Blauen Kreis über dem Rechteck
Bitmap::drawCircle(bild, 100, 100, 40, blau);

// Einzelnen Pixel lesen und ausgeben
let px: Int64 = Bitmap::getPixel(bild, 100, 100);
print("Pixel (100,100): " + px.toString() + "\n");

// Einzelnen Pixel überschreiben
Bitmap::setPixel(bild, 100, 100, schwarz);
print("Pixel nach Überschreiben: " + Bitmap::getPixel(bild, 100, 100).toString() + "\n");

tpl

import tinox.core.tpl;

Das Modul tpl bietet eine einfache Vorlagen-Engine (Template Engine) im Mustache-Stil. Templates verwenden {{schluessel}}-Platzhalter, die durch Datenwerte ersetzt werden. Neben dem direkten Rendern können Templates vorkompiliert (compile) und anschließend effizient wiederholt ausgeführt (execute) werden. Eine Schleifenfunktion ermöglicht das Rendern einer Vorlage für mehrere Datensätze.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Template::render fn render(template: String, data: Map<String, JsonValue>) -> String Ersetzt alle {{schluessel}}-Platzhalter in template durch die entsprechenden Werte aus data.
Template::renderLoop fn renderLoop(template: String, items: List<Map<String, JsonValue>>, itemVar: String) -> String Rendert template für jedes Element in items und konkateniert die Ergebnisse.
Template::compile fn compile(template: String) -> CompiledTemplate Parst template in eine Liste von TemplateSection-Abschnitten (text / var / section / end).
Template::execute fn execute(tpl: CompiledTemplate, data: Map<String, JsonValue>) -> String Führt ein bereits kompiliertes Template mit den angegebenen Daten aus.
CompiledTemplate source: String; sections: List<TemplateSection> Datenstruktur: Vorcompiliertes Template mit Quelltext und Abschnitts-Liste.
TemplateSection kind: String; content: String Datenstruktur: Ein Abschnitt des Templates; kind ist "text", "var", "section" oder "end".

Beispiel

import tinox.core.tpl;

// Einfaches direktes Rendering
let vorlage: String = "Hallo, {{name}}! Du hast {{punkte}} Punkte.";
let daten: Map<String, JsonValue> = Map::new();
daten["name"]   = JsonValue::fromString("Maria");
daten["punkte"] = JsonValue::fromInt(1340);

let ausgabe: String = Template::render(vorlage, daten);
print(ausgabe + "\n");
// Ausgabe: Hallo, Maria! Du hast 1340 Punkte.

// Vorlagen-Schleife über mehrere Datensätze
let zeilenVorlage: String = "- {{titel}} ({{jahr}})\n";
let filme: List<Map<String, JsonValue>> = [];

let film1: Map<String, JsonValue> = Map::new();
film1["titel"] = JsonValue::fromString("Inception");
film1["jahr"]  = JsonValue::fromInt(2010);
filme.push(film1);

let film2: Map<String, JsonValue> = Map::new();
film2["titel"] = JsonValue::fromString("Dune");
film2["jahr"]  = JsonValue::fromInt(2021);
filme.push(film2);

let liste: String = Template::renderLoop(zeilenVorlage, filme, "film");
print(liste);

// Vorkompiliertes Template für Wiederverwendung
let compiled: CompiledTemplate = Template::compile("Benutzer: {{login}} | Rolle: {{rolle}}");

let admin: Map<String, JsonValue> = Map::new();
admin["login"] = JsonValue::fromString("admin");
admin["rolle"] = JsonValue::fromString("Administrator");
print(Template::execute(compiled, admin) + "\n");

import tinox.core.crypto;

Das Modul crypto stellt kryptographische Grundfunktionen bereit: Hashverfahren (MD5, SHA-256), HMAC-Signaturen, symmetrische AES-Verschlüsselung, sichere Schlüsselgenerierung und passwortbasierte Schlüsselableitung über PBKDF2.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Crypto::md5fn md5(data: String) -> StringBerechnet den MD5-Hash der übergebenen Zeichenkette und gibt ihn als Hex-String zurück.
Crypto::sha256fn sha256(data: String) -> StringBerechnet den SHA-256-Hash der übergebenen Zeichenkette und gibt ihn als Hex-String zurück.
Crypto::hmacSha256fn hmacSha256(data: String, key: String) -> StringErzeugt eine HMAC-SHA-256-Signatur der Daten mit dem angegebenen Schlüssel.
Crypto::aesEncryptfn aesEncrypt(data: String, key: String) -> StringVerschlüsselt die Daten mit AES-256-GCM (authentifiziert). key darf beliebig lang sein (wird intern per SHA-256 zu einem 256-Bit-Schlüssel abgeleitet). Rückgabe ist Hex-kodiert (Nonce + Ciphertext + Auth-Tag), pro Aufruf mit neuer Zufalls-Nonce — zweimaliges Verschlüsseln derselben Daten liefert unterschiedliche Ergebnisse. Wirft bei Fehler (z. B. Modul oauth2, issue #131). Wirft bei Fehler statt einer zu kurzen Liste.

Beispiel

import tinox.core.crypto;

// Einfacher SHA-256-Hash
let digest: String = Crypto::sha256("Hallo Welt");
println("SHA-256: " + digest);

// HMAC-Signatur prüfen
let secret: String = "meinGeheimnis";
let sig: String = Crypto::hmacSha256("Nutzdaten", secret);
println("HMAC: " + sig);

// Zufälligen AES-Schlüssel erzeugen und Daten verschlüsseln
let key: String = Crypto::generateKey(32);
let cipher: String = Crypto::aesEncrypt("Geheime Nachricht", key);
let plain: String  = Crypto::aesDecrypt(cipher, key);
println("Entschlüsselt: " + plain);

// Passwort-Hashing via PBKDF2
let salt: String    = Crypto::generateKey(16);
let derived: String = Crypto::pbkdf2("passwort123", salt, 10000, 32);
println("Abgeleiteter Schlüssel: " + derived);

pool

import tinox.core.pool;

Das Modul pool stellt einen generischen Objekt-Pool bereit. Teure Objekte (z. B. Datenbankverbindungen, Netzwerk-Sockets) werden im Pool vorgehalten und wiederverwendet, anstatt bei jedem Bedarf neu erzeugt zu werden. Die maximale Poolgröße ist konfigurierbar.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Pool::newfn new(maxSize: Int64) -> Pool<T>Erstellt einen neuen Pool mit der angegebenen maximalen Größe.
Pool::acquirefn acquire(pool: Pool<T>) -> TGibt ein verfügbares Objekt aus dem Pool zurück oder erzeugt ein neues, sofern die Maximalgröße nicht erreicht ist. Wirft "Pool exhausted", wenn der Pool voll ist.
Pool::releasefn release(pool: Pool<T>, obj: T) -> NothingGibt ein verwendetes Objekt an den Pool zurück, damit es wiederverwendet werden kann.
Pool::clearfn clear(pool: Pool<T>) -> NothingEntfernt alle Objekte aus dem Pool (verfügbare und in Verwendung befindliche).

Beispiel

import tinox.core.pool;

// Pool für Datenbankverbindungen (maximal 5)
let dbPool: Pool<DbConnection> = Pool::new(5);

// Verbindung holen
let conn: DbConnection = Pool::acquire(dbPool);
let ergebnis: List<Row> = conn.query("SELECT * FROM nutzer");
println("Zeilen: " + ergebnis.len().toString());

// Verbindung zurückgeben
Pool::release(dbPool, conn);

// Zweite Verbindung – wird aus dem Pool wiederverwendet
let conn2: DbConnection = Pool::acquire(dbPool);
conn2.execute("UPDATE nutzer SET aktiv = 1 WHERE id = 42");
Pool::release(dbPool, conn2);

// Pool leeren (z. B. beim Herunterfahren)
Pool::clear(dbPool);
println("Pool wurde geleert.");

ratelimit

import tinox.core.ratelimit;

Das Modul ratelimit implementiert zwei Strategien zur Anfragebegrenzung: RateLimiter verwendet ein Sliding-Window-Verfahren (festes Zeitfenster), während TokenBucket das Token-Bucket-Verfahren mit konfigurierbarer Nachfüllrate einsetzt.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
RateLimiter::newfn new(maxRequests: Int64, windowMs: Int64) -> RateLimiterErstellt einen neuen Rate-Limiter mit maximaler Anfrageanzahl und Zeitfenster in Millisekunden.
RateLimiter::allowfn allow(limiter: RateLimiter) -> BoolPrüft, ob eine weitere Anfrage erlaubt ist. Gibt true zurück und registriert die Anfrage, oder false, wenn das Limit erreicht ist.
RateLimiter::resetfn reset(limiter: RateLimiter) -> NothingSetzt alle registrierten Anfragen zurück.
RateLimiter::remainingfn remaining(limiter: RateLimiter) -> Int64Gibt die Anzahl der noch erlaubten Anfragen im aktuellen Zeitfenster zurück.
TokenBucket::newfn new(capacity: Int64, refillRate: Float64) -> TokenBucketErstellt einen Token-Bucket mit Kapazität und Nachfüllrate (Tokens pro Sekunde).
TokenBucket::allowfn allow(bucket: TokenBucket) -> BoolPrüft, ob ein Token verfügbar ist. Füllt zuvor nach und gibt true zurück, wenn ein Token entnommen werden konnte.
TokenBucket::refillfn refill(bucket: TokenBucket) -> NothingFüllt den Bucket basierend auf der vergangenen Zeit seit dem letzten Auffüllen nach.

Beispiel

import tinox.core.ratelimit;

// Sliding-Window: 100 Anfragen pro Minute
let limiter: RateLimiter = RateLimiter::new(100, 60000);

var i: Int64 = 0;
while i < 5
{
    if RateLimiter::allow(limiter)
    {
        println("Anfrage " + i.toString() + " erlaubt. Verbleibend: "
                + RateLimiter::remaining(limiter).toString());
    }
    i = i + 1;
}

// Token-Bucket: Kapazität 10, 2 Token/Sekunde
let bucket: TokenBucket = TokenBucket::new(10, 2.0);

if TokenBucket::allow(bucket)
{
    println("Anfrage über Token-Bucket erlaubt.");
}
else
{
    println("Token-Bucket leer – Anfrage abgelehnt.");
}

cron

import tinox.core.cron;

Das Modul cron ermöglicht die Planung wiederkehrender Aufgaben über Cron-Ausdrücke im Unix-Format (5 Felder: Minute, Stunde, Tag, Monat, Wochentag). Der CronScheduler verwaltet mehrere Jobs und führt sie beim Aufruf von tick aus, wenn die Bedingung zutrifft.

Cron::nextRunfn nextRun(expr: CronExpr) -> Int64Berechnet den Zeitstempel (ms seit Epoch) des nächsten geplanten Laufs.

Cron::getCurrentMinutefn getCurrentMinute(sec: Int64) -> Int64Hilfsfunktion: Berechnet die aktuelle Minute (0–59) aus einem Unix-Timestamp in Sekunden.
Cron::matchesfn matches(expr: CronExpr, timestamp: Int64) -> BoolPrüft, ob ein Cron-Ausdruck für den angegebenen Zeitstempel zutrifft.
CronScheduler::newfn new() -> CronSchedulerErstellt einen neuen, gestoppten Scheduler ohne Jobs.
CronScheduler::addJobfn addJob(scheduler: CronScheduler, expr: String, callback: fnc() -> Nothing) -> NothingRegistriert einen neuen Job mit Cron-Ausdruck und Callback-Funktion.
CronScheduler::startfn start(scheduler: CronScheduler) -> NothingAktiviert den Scheduler, sodass tick-Aufrufe Jobs ausführen.
CronScheduler::stopfn stop(scheduler: CronScheduler) -> NothingDeaktiviert den Scheduler; weitere tick-Aufrufe werden ignoriert.

Beispiel

import tinox.core.cron;

let scheduler: CronScheduler = CronScheduler::new();

// Jede Minute ausführen
CronScheduler::addJob(scheduler, "* * * * *", () => {
    println("Minütlicher Job läuft.");
});

// Täglich um 08:30 ausführen
CronScheduler::addJob(scheduler, "30 8 * * *", () => {
    println("Täglicher Morgenbericht wird erstellt.");
});

CronScheduler::start(scheduler);

// Haupt-Schleife (tick z. B. alle 60 s aufrufen)
var tick: Int64 = 0;
while tick < 3
{
    CronScheduler::tick(scheduler);
    tick = tick + 1;
}

CronScheduler::stop(scheduler);
println("Scheduler gestoppt.");

import tinox.core.events;

Das Modul events implementiert das Observer-Muster über einen EventEmitter. Listener können für benannte Ereignisse registriert, einmalig abonniert oder wieder entfernt werden. Beim Auslösen eines Ereignisses werden alle registrierten Handler mit einem JsonValue-Payload aufgerufen.

EventEmitter::oncefn once(emitter: EventEmitter, event: String, handler: fnc(JsonValue) -> Nothing) -> NothingRegistriert einen Listener, der beim ersten Auftreten des Ereignisses ausgeführt wird.
EventEmitter::emitfn emit(emitter: EventEmitter, event: String, data: JsonValue) -> NothingLöst das angegebene Ereignis aus und übergibt den Payload an alle registrierten Handler.

Beispiel

import tinox.core.events;

let emitter: EventEmitter = EventEmitter::new();

// Dauerhafter Listener
EventEmitter::on(emitter, "bestellung", (data: JsonValue) => {
    println("Neue Bestellung: " + data.toString());
});

// Einmaliger Listener
EventEmitter::once(emitter, "start", (data: JsonValue) => {
    println("Anwendung gestartet.");
});

println("Anzahl Listener für 'bestellung': "
        + EventEmitter::listenerCount(emitter, "bestellung").toString());

// Ereignisse auslösen
EventEmitter::emit(emitter, "start", Json::null());
EventEmitter::emit(emitter, "bestellung", Json::parse("{\"id\": 42}"));

// Alle Listener entfernen
EventEmitter::removeAllListeners(emitter, "bestellung");
println("Listener nach Entfernung: "
        + EventEmitter::listenerCount(emitter, "bestellung").toString());

import tinox.core.cache;

Das Modul cache bietet einen generischen LRU-Cache (Least Recently Used). Bei Erreichen der maximalen Größe wird der am längsten nicht verwendete Eintrag automatisch verdrängt. Die Klasse LruCache ist ein schlanker Wrapper um die interne Cache-Klasse.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Cache::newfn new(maxSize: Int64) -> Cache<K, V>Erstellt einen neuen Cache mit der angegebenen maximalen Eintragsanzahl.
Cache::getfn get(cache: Cache<K, V>, key: K) -> Option<V>Gibt den Wert zum Schlüssel als Option zurück und aktualisiert die Zugriffsreihenfolge.
Cache::setfn set(cache: Cache<K, V>, key: K, value: V) -> NothingSetzt einen Eintrag. Bei Überschreitung der Maximalgröße wird der älteste Eintrag entfernt.
Cache::removefn remove(cache: Cache<K, V>, key: K) -> BoolEntfernt den Eintrag mit dem angegebenen Schlüssel. Gibt true zurück, wenn der Schlüssel vorhanden war.
Cache::clearfn clear(cache: Cache<K, V>) -> NothingEntfernt alle Einträge aus dem Cache.
Cache::touchfn touch(cache: Cache<K, V>, key: K) -> NothingMarkiert einen Schlüssel als zuletzt verwendet (verschiebt ihn ans Ende der LRU-Liste).
LruCache::newfn new(maxSize: Int64) -> LruCache<K, V>Erstellt einen neuen LRU-Cache-Wrapper mit der angegebenen Maximalgröße.
LruCache::getfn get(cache: LruCache<K, V>, key: K) -> Option<V>Gibt den Wert zum Schlüssel als Option zurück.
LruCache::setfn set(cache: LruCache<K, V>, key: K, value: V) -> NothingSetzt einen Eintrag im LRU-Cache.

Beispiel

import tinox.core.cache;

// LRU-Cache mit maximal 3 Einträgen
let lru: LruCache<String, String> = LruCache::new(3);

LruCache::set(lru, "a", "Apfel");
LruCache::set(lru, "b", "Banane");
LruCache::set(lru, "c", "Kirsche");

// Eintrag lesen
let val: Option<String> = LruCache::get(lru, "b");
if val.isSome()
{
    println("Gefunden: " + val.unwrap());
}

// Vierter Eintrag verdrängt den ältesten (hier "a")
LruCache::set(lru, "d", "Dattel");

let alt: Option<String> = LruCache::get(lru, "a");
println("'a' noch im Cache: " + alt.isSome().toString());

// Cache leeren
Cache::clear(lru.cache);
println("Cache geleert.");

import tinox.core.option;

Das Modul option stellt den generischen Typ Option<T> bereit, der entweder einen Wert (Some) oder das Fehlen eines Wertes (None) darstellt. Intern wird eine List<T> verwendet, um die Notwendigkeit eines Null-Wertes für T zu umgehen.

Klassen & Methoden

Klasse / MethodeSignaturBeschreibung
Option::nonefn none() -> Option<T>Erstellt eine leere Option (kein Wert).
Option::somefn some(value: T) -> Option<T>Erstellt eine Option, die den angegebenen Wert enthält.
Option::isSomefn isSome() -> BoolGibt true zurück, wenn die Option einen Wert enthält.
Option::isNonefn isNone() -> BoolGibt true zurück, wenn die Option leer ist.
Option::unwrapfn unwrap() -> TGibt den enthaltenen Wert zurück. Wirft "Option is None", wenn die Option leer ist.
Option::unwrapOrfn unwrapOr(defaultValue: T) -> TGibt den enthaltenen Wert oder den angegebenen Standardwert zurück, wenn die Option leer ist.
Option::mapfn map<U>(transform: fnc(T) -> U) -> Option<U>Wendet eine Transformationsfunktion auf den enthaltenen Wert an und gibt eine neue Option zurück.
Option::andThenfn andThen<U>(transform: fnc(T) -> Option<U>) -> Option<U>Verkettung: Wendet eine Funktion an, die selbst eine Option zurückgibt (Flatmap).
Option::orElsefn orElse(fallback: fnc() -> Option<T>) -> Option<T>Gibt die aktuelle Option zurück, wenn sie einen Wert hat; andernfalls das Ergebnis des Fallback-Aufrufs.

Beispiel

import tinox.core.option;

fn sucheNutzer(id: Int64) -> Option<String>
{
    if id == 1
    {
        return Option::some("Alice");
    }
    return Option::none();
}

// Wert extrahieren mit Fallback
let name: String = sucheNutzer(1).unwrapOr("Unbekannt");
println("Gefunden: " + name);

// Transformation mit map
let gross: Option<String> = sucheNutzer(1).map(n => n.toUpperCase());
println("Großschreibung: " + gross.unwrapOr("–"));

// Verkettung mit andThen
let ergebnis: Option<Int64> = sucheNutzer(1)
    .andThen(n => {
        if n.len() > 3 { return Option::some(n.len()); }
        return Option::none();
    });
println("Länge: " + ergebnis.unwrapOr(0).toString());

// orElse-Fallback
let alternativ: Option<String> = sucheNutzer(99)
    .orElse(() => Option::some("Gast"));
println("Alternativ: " + alternativ.unwrap());

Das Modul result stellt den generischen Typ Result<T> bereit, der entweder einen Erfolgswert (Ok) oder eine Fehlermeldung als String (Err) darstellt. Es ermöglicht explizite, typsichere Fehlerbehandlung ohne Ausnahmen.

Beispiel

import tinox.core.result;

fn dividiere(a: Int64, b: Int64) -> Result<Int64>
{
    if b == 0
    {
        return Result::err("Division durch null");
    }
    return Result::ok(a / b);
}

// Einfache Verwendung
let r: Result<Int64> = dividiere(10, 2);
if r.isOk()
{
    println("Ergebnis: " + r.unwrap().toString());
}

// Fehlerfall
let fehler: Result<Int64> = dividiere(5, 0);
println("Fehler: " + fehler.getError());
println("Fallback: " + fehler.unwrapOr(-1).toString());

// Verkettung
let kette: Result<String> = dividiere(100, 4)
    .map(n => "Wert: " + n.toString())
    .mapErr(e => "Berechnung fehlgeschlagen – " + e);
println(kette.unwrapOr("Kein Ergebnis"));

logger

Das Modul logger bietet ein strukturiertes Logging-System mit konfigurierbaren Log-Levels. Jeder Logger besitzt einen Namen und gibt Meldungen mit Zeitstempel, Level und Namen aus. Die Klasse LogLevel definiert die vier Stufen Debug, Info, Warn und Error.

Tinox bietet ein typsicheres ORM nach dem JPA/QueryDSL-Prinzip. Klassen werden mit Annotations als Datenbank-Tabellen markiert. Abfragen laufen ausschließlich über ein Lambda-DSL — keine String-basierten Queries.

Fehlerbehandlung

Datenbankfehler werden aktuell auf stderr protokolliert. Eine try/catch-Integration ist für eine spätere Version geplant. Verbindungsfehler beim Start beenden das Programm mit einer aussagekräftigen Fehlermeldung.
