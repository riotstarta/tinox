# Tinox ORM — Implementierungs-Roadmap

Ziel: JPA/QueryDSL-ähnliches ORM für Tinox. Klassen werden mit Annotations als DB-Tabellen markiert.
Abfragen laufen ausschließlich über ein typsicheres Lambda-DSL — keine String-basierten Queries.

```tinox
@Entity
@Table("users")
class User {
    @Id @GeneratedValue
    var id: Int64;
    @Column("name")
    var name: String;
    @Column("age")
    var age: Int64;
}

// Verwendung:
let adults: List<User> = DB.of(User)
    .filter(u -> u.age > 18)
    .orderBy(u -> u.name)
    .limit(10)
    .list();
```

### 1.4 Verarbeitung in `process_class_annotations()` ✅

In der match-Schleife über `class.annotations`:

```rust
"Entity" | "Table" => { /* merken, später auswerten */ }
```

Nach der Schleife: wenn `@Entity` oder `@Table` vorhanden, EntityInfo aufbauen:

```rust
let has_entity = class.annotations.iter().any(|a| a.name == "Entity" || a.name == "Table");
if has_entity {
    let table_name = class.annotations.iter()
        .find(|a| a.name == "Table")
        .and_then(|a| a.args.first())
        .and_then(|arg| if let AnnotationArg::Literal(Literal::String(s)) = arg { Some(s.clone()) } else { None })
        .unwrap_or_else(|| class.name.to_lowercase());

    let fields = class.fields.iter().map(|f| {
        let col_name = f.annotations.iter()
            .find(|a| a.name == "Column")
            .and_then(|a| a.args.first())
            .and_then(|arg| if let AnnotationArg::Literal(Literal::String(s)) = arg { Some(s.clone()) } else { None })
            .unwrap_or_else(|| f.name.clone());
        EntityFieldInfo {
            field_name: f.name.clone(),
            column_name: col_name,
            is_id: f.annotations.iter().any(|a| a.name == "Id"),
            is_generated: f.annotations.iter().any(|a| a.name == "GeneratedValue"),
            not_null: f.annotations.iter().any(|a| a.name == "NotNull"),
            field_llvm_type: field_type_to_llvm(&f.field_type),
        }
    }).collect();

    result.entity_entries.push(EntityInfo {
        class_name: class.name.clone(),
        table_name,
        fields,
    });
}
```

### 2.4 `emit_entity_code()` — SQL-Konstanten und Mapping-Funktionen ✅

Neue Methode `fn emit_entity_code(&mut self)`, aufgerufen am Ende von `gen()`.

Für jede `EntityEntry` folgende LLVM-IR-Funktionen generieren:

#### `ClassName_selectSql() -> i8*`
Gibt `"SELECT col1, col2, ... FROM table_name"` zurück.
Nur Nicht-generierte Felder für INSERT, alle Felder für SELECT.

#### `ClassName_insertSql() -> i8*`
Gibt `"INSERT INTO table (col1, col2) VALUES ($1, $2) RETURNING id"` zurück.
`@GeneratedValue`-Felder weglassen.

#### `ClassName_updateSql() -> i8*`
Gibt `"UPDATE table SET col1=$1, col2=$2 WHERE id=$N"` zurück.
`@Id`-Feld in WHERE, alle anderen in SET.

#### `ClassName_deleteSql() -> i8*`
Gibt `"DELETE FROM table WHERE id=$1"` zurück.

#### `ClassName_fromRow(result: i8*, row_idx: i64) -> i64*`
Alloziert eine neue Instanz via `tinox_alloc`, liest alle Spalten per
`tinox_db_getval(result, row_idx, col_idx)` und schreibt sie in die Felder.
String-Felder: direkt als i8*.
Int64-Felder: `tinox_string_to_int(val)`.
Bool-Felder: Vergleich mit "true".

#### `ClassName_toParams(entity: i64*, out_n: i64*) -> i8**`
Alloziert i8**-Array mit Anzahl der nicht-ID-Felder (für INSERT) oder
allen Feldern (für UPDATE). Konvertiert Int64 via `tinox_int_to_string`.
Schreibt Anzahl in `*out_n`.

### 2.5 Lambda → SQL Übersetzung ✅

Das ist das Kernstück. Der Codegen analysiert Lambda-Ausdrücke die an
`.filter()`, `.orderBy()`, `.sum()` übergeben werden.

**Implementierung:** Neue Funktion `fn lambda_to_sql_predicate(expr: &Expr, param_offset: usize) -> (String, Vec<LlvmValue>)`

Übersetzungstabelle:

| Lambda-Ausdruck | SQL-Fragment | Parameter |
|---|---|---|
| `u.age > 18` | `age > $N` | [18] |
| `u.age >= 18` | `age >= $N` | [18] |
| `u.name == "Alice"` | `name = $N` | ["Alice"] |
| `u.name != "Bob"` | `name != $N` | ["Bob"] |
| `u.active == true` | `active = $N` | ["true"] |
| `u.name.startsWith("A")` | `name LIKE $N` | ["A%"] |
| `u.name.endsWith("z")` | `name LIKE $N` | ["%z"] |
| `u.name.contains("foo")` | `name LIKE $N` | ["%foo%"] |
| `expr1 && expr2` | `(pred1) AND (pred2)` | params kombiniert |
| `expr1 \|\| expr2` | `(pred1) OR (pred2)` | params kombiniert |
| `!expr` | `NOT (pred)` | params |

Für `.orderBy(u -> u.name)` → extrahiere Feldname → `ORDER BY col_name ASC`
Für `.orderByDesc(u -> u.name)` → `ORDER BY col_name DESC`
Für `.sum(u -> u.total)` → `SUM(col_name)` statt `*`

Die generierten WHERE-Fragmente werden als String-Konstanten ins IR emittiert,
oder zur Laufzeit via `tinox_string_concat` zusammengebaut wenn nötig.

## Phase 3 — C-Runtime: libpq PostgreSQL ✅

**Datei:** `runtime/runtime.c`

### 3.1 Header und globale Connection ✅

```c
#include <libpq-fe.h>

static PGconn* _tinox_db_conn = NULL;
static pthread_mutex_t _tinox_db_mu = PTHREAD_MUTEX_INITIALIZER;

void tinox_db_connect(const char* url) {
    _tinox_db_conn = PQconnectdb(url);
    if (PQstatus(_tinox_db_conn) != CONNECTION_OK) {
        fprintf(stderr, "DB connection failed: %s\n", PQerrorMessage(_tinox_db_conn));
        PQfinish(_tinox_db_conn);
        exit(1);
    }
}

PGconn* tinox_db_get_conn(void) {
    return _tinox_db_conn;
}
```

### 3.2 Query-Ausführung ✅

```c
// params: i8** Array mit n_params Strings (NULL-terminiert pro String)
// Gibt PGresult* zurück (als i8* für LLVM)
void* tinox_db_exec(void* conn, const char* sql, const char** params, int64_t n_params) {
    PGresult* res = PQexecParams(
        (PGconn*)conn, sql,
        (int)n_params, NULL,
        params, NULL, NULL, 0
    );
    ExecStatusType status = PQresultStatus(res);
    if (status != PGRES_TUPLES_OK && status != PGRES_COMMAND_OK) {
        fprintf(stderr, "Query error: %s\nSQL: %s\n", PQresultErrorMessage(res), sql);
        // Nicht exit() — Result zurückgeben, Fehler per tinox_db_error() abrufbar
    }
    return (void*)res;
}

int64_t tinox_db_nrows(void* result) { return PQntuples((PGresult*)result); }
int64_t tinox_db_ncols(void* result) { return PQnfields((PGresult*)result); }

char* tinox_db_getval(void* result, int64_t row, int64_t col) {
    return GC_strdup(PQgetvalue((PGresult*)result, (int)row, (int)col));
}

bool tinox_db_is_null(void* result, int64_t row, int64_t col) {
    return PQgetisnull((PGresult*)result, (int)row, (int)col);
}

void tinox_db_free(void* result) { PQclear((PGresult*)result); }

char* tinox_db_error(void* conn) {
    return GC_strdup(PQerrorMessage((PGconn*)conn));
}
```

### 3.3 Param-Helpers ✅

## Phase 5 — Stdlib: Lambda-Query-DSL ✅

**Datei:** `crates/tinox-core/db.tnx`

**Wichtig:** Die Klassen hier sind API-Wrapper. Die eigentliche SQL-Generierung aus Lambdas
passiert in Phase 2 (Codegen) zur Compile-Zeit. Die Stdlib-Klassen rufen die generierten
`ClassName_selectSql()`, `ClassName_fromRow()` etc. auf.

```tinox
module tinox.core.db;

namespace tinox.core.db
{
    class EntityQuery<T>
    {
        // filter(), orderBy() etc. bauen intern WHERE/ORDER BY Fragmente auf.
        // Die Lambdas werden vom Compiler analysiert und in SQL übersetzt.

        fn filter(predicate: fnc(T) -> Bool) -> EntityQuery<T>
        fn orderBy(field: fnc(T) -> Any) -> EntityQuery<T>
        fn orderByDesc(field: fnc(T) -> Any) -> EntityQuery<T>
        fn limit(n: Int64) -> EntityQuery<T>
        fn offset(n: Int64) -> EntityQuery<T>

        fn list() -> List<T>
        fn first() -> T
        fn count() -> Int64
        fn sum(field: fnc(T) -> Int64) -> Int64

        fn save(entity: T) -> T
        fn delete(entity: T) -> Nothing
        fn saveAll(entities: List<T>) -> Nothing
    }

    class DB
    {
        fn of<T>() -> EntityQuery<T>
        {
            return EntityQuery<T> {};
        }
    }
}
```

Die interne Implementierung von `list()` ruft z.B.:
```tinox
fn list(query: EntityQuery<T>) -> List<T> {
    let sql: String = T_selectSql();           // generiert
    let whereSql: String = query.whereClause;  // aus filter()-Lambdas
    let fullSql: String = sql + " WHERE " + whereSql + query.orderSql + query.limitSql;
    let conn: Int64 = __tinox_db_get_conn();
    let result: Int64 = __tinox_db_exec(conn, fullSql, query.params, query.paramCount);
    let rows: List<T> = List::new();
    let n: Int64 = __tinox_db_nrows(result);
    let i: Int64 = 0;
    while i < n {
        rows.add(T_fromRow(result, i));        // generiert
        i = i + 1;
    }
    __tinox_db_free(result);
    return rows;
}
```

## Phase 6 — C-Runtime: MySQL ✅

**Datei:** `runtime/runtime.c`

Analog zu Phase 3, aber mit `libmysqlclient`:

- `#include <mysql/mysql.h>`
- Globale `MYSQL* _tinox_mysql_conn`
- `tinox_mysql_connect(host, user, pass, db, port)` via `mysql_real_connect()`
- `tinox_mysql_exec(conn, sql, params, n)` via Prepared Statements (`mysql_stmt_*`)
  - Wichtig: MySQL nutzt `?` statt `$1` als Platzhalter
  - Parameter-Binding via `MYSQL_BIND`-Array
- `tinox_mysql_nrows / getval / free / error` analog

**Driver-Abstraktion:** In der Config-Auswertung (`read_database_config()`) entscheiden
ob Postgres- oder MySQL-Funktionen aufgerufen werden. Entweder:
- Separate Funktionsnamen: `tinox_pg_exec` vs `tinox_mysql_exec`
- Oder: Adapter-Pointer: `static void* (*tinox_db_exec_fn)(...)` der beim Connect gesetzt wird.

Empfohlen: Adapter-Pointer-Ansatz, damit Stdlib-Code driver-agnostisch bleibt.

Linker-Flag: `-lmysqlclient`

## Phase 7 — C-Runtime: SQLite ✅

static sqlite3* _tinox_sqlite_db = NULL;

void tinox_sqlite_open(const char* path) {
