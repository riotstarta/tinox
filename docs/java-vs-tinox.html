📝 Syntax & Grundkonstrukte

Hello World

Java

public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}

Tinox

fn main() -> Int64
{
    println("Hello, World!");
    return 0;
}

TypeScript

console.log("Hello, World!");

Variablen & Inferenz

Java

final int x = 42;           // immutable
int y = 10;                  // mutable
var name = "Alice";          // Inferenz (Java 10+)
String msg = "Hi " + name + "!"; // kein Interpolation

Tinox

let x: Int64 = 42;           // immutable
var y: Int64 = 10;           // mutable
let name = "Alice";          // Inferenz überall
let msg = "Hi ${name}!";     // String-Interpolation

TypeScript

const x: number = 42;        // immutable
let y: number = 10;          // mutable
const name = "Alice";        // Inferenz
const msg = `Hi ${name}!`;   // Template Literal

Schleifen & Ranges

Java

for (int i = 0; i < 5; i++) {
    System.out.println(i);
}
// for-each
for (String s : list) {
    System.out.println(s);
}
// IntStream-Range
IntStream.rangeClosed(0, 5)
         .forEach(System.out::println);

Tinox

for i in 0..5        // exklusiv: 0,1,2,3,4
{
    println(i);
}

for i in 0...5       // inklusiv: 0,1,2,3,4,5
{
    println(i);
}

for ch in "hello"    // Zeichen-Iteration
{
    print(ch);
}

TypeScript

for (let i = 0; i < 5; i++) {
    console.log(i);
}
// for-of
for (const s of list) {
    console.log(s);
}
// Array-Range via spread
[...Array(5).keys()]
    .forEach(i => console.log(i));

Tinox — Syntax-Vorteile

  • Deutlich weniger Boilerplate (kein public class Wrapper)
  • let/var macht Mutability sofort sichtbar
  • String-Interpolation direkt in der Sprache
  • Ranges (0..5, 0...5) statt Iterator-APIs
  • Allman-Style Formatter erzwingt einheitlichen Stil

Tinox — Syntax-Nachteile

  • Jüngere Sprache, weniger bekannte Konventionen
  • Allman-Style kann polarisieren
  • Kein REPL (noch in Planung)
  • Kleinere Community, weniger Tutorials

🧬 Typen & Generics

Generics

Java

// Type Erasure: T wird zur Laufzeit zu Object
public class Box<T> {
    private T value;

    public Box(T value) { this.value = value; }
    public T get() { return value; }
}

Box<Integer> b = new Box<>(42);
// Wildcards: Box<? extends Number>
// Kein Box<int>, nur Box<Integer>

Tinox

// Monomorphisierung: echter Typ bleibt erhalten
class Box<T>
{
    value: T;

    fn get() -> T
    {
        return this.value;
    }
}

let b = new Box<Int64>(42);
// Primitive direkt verwendbar (kein Boxing)

TypeScript

// Strukturelles Typsystem, zur Compile-Zeit gelöscht
class Box<T> {
    constructor(private value: T) {}
    get(): T { return this.value; }
}

const b = new Box<number>(42);
// Constraints: Box<T extends number>
// Conditional Types: T extends U ? X : Y

Collections

Java

List<String> list = new ArrayList<>();
list.add("hello");
list.size();
list.get(0);

Map<String, Integer> map = new HashMap<>();
map.put("a", 1);
map.get("a");
map.containsKey("a");

Tinox

let arr = ["hello"];
arr.push("world");
arr.len();
arr[0];

let m = @{"a" => 1};
m.insert("b", 2);
m.get("a");
m.contains("a");
// oder typisiert:
let m: Map<String, Int64> = Map::new();

TypeScript

const list: string[] = [];
list.push("hello");
list.length;
list[0];

const map = new Map<string, number>();
map.set("a", 1);
map.get("a");
map.has("a");
// Object-Literal als Map:
const obj: Record<string, number> = { a: 1 };

Tinox Generics — Vorteile

  • Monomorphisierung: kein Overhead durch Type Erasure
  • Primitive direkt als Typparameter (kein Integer vs. int)
  • Map-Literal-Syntax (@{"k" => v}) kompakter
  • Array-Builtins (first, last, join) ohne Import

Tinox Generics — Nachteile

  • Monomorphisierung kann Binärgröße erhöhen
  • Wildcards (? extends T) nicht vorhanden
  • Bounded Type Parameters noch eingeschränkt
  • Kein Reflection-Zugriff auf Typinformation

🏗️ OOP, Klassen & Vererbung

Java

public abstract class Animal {
    protected String name;

    public Animal(String name) {
        this.name = name;
    }

    public abstract String speak();
}

public class Dog extends Animal {
    public Dog(String name) { super(name); }

    @Override
    public String speak() {
        return "Woof! I am " + name;
    }
}

Animal a = new Dog("Rex");
System.out.println(a.speak());

Tinox

class Animal
{
    name: String;

    fn speak() -> String
    {
        return "...";
    }
}

class Dog extends Animal
{
    fn speak() -> String
    {
        return "Woof! I am ${this.name}";
    }
}

let a: Animal = new Dog();
a.name = "Rex";
println(a.speak());

TypeScript

abstract class Animal {
    constructor(protected name: string) {}
    abstract speak(): string;
}

class Dog extends Animal {
    speak(): string {
        return `Woof! I am ${this.name}`;
    }
}

const a: Animal = new Dog("Rex");
console.log(a.speak());

Interfaces

Java

public interface Printable {
    String toString();
    // Default-Methoden möglich:
    default void print() {
        System.out.println(toString());
    }
}

public class Point implements Printable {
    int x, y;
    public Point(int x, int y) { this.x=x; this.y=y; }

    @Override
    public String toString() {
        return "(" + x + ", " + y + ")";
    }
}

Tinox

interface Printable
{
    fn toString() -> String;
}

class Point implements Printable
{
    var x: Int64;
    var y: Int64;

    fnc new(x: Int64, y: Int64) -> Point
    {
        return Point { x: x, y: y };
    }

    fn toString() -> String
    {
        return "(${this.x}, ${this.y})";
    }
}

// vtable-basierter Dispatch

TypeScript

interface Printable {
    toString(): string;
}

class Point implements Printable {
    constructor(
        public x: number,
        public y: number
    ) {}

    toString(): string {
        return `(${this.x}, ${this.y})`;
    }
}

// Strukturelles Typing: Duck Typing

Statische Methoden & Konstruktoren

Java

public class Point {
    public final int x, y;

    // Konstruktor
    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    // Statische Factory-Methode
    public static Point origin() {
        return new Point(0, 0);
    }

    // Statische Methode
    public static int add(int a, int b) {
        return a + b;
    }
}

Tinox

class Point
{
    var x: Int64;
    var y: Int64;

    // fnc = statisch
    fnc new(x: Int64, y: Int64) -> Point
    {
        return Point { x: x, y: y };
    }

    fnc origin() -> Point
    {
        return Point::new(0, 0);
    }

    fnc add(a: Int64, b: Int64) -> Int64
    {
        return a + b;
    }
}

TypeScript

class Point {
    constructor(
        public readonly x: number,
        public readonly y: number
    ) {}

    // Statische Factory-Methode
    static origin(): Point {
        return new Point(0, 0);
    }

    // Statische Methode
    static add(a: number, b: number): number {
        return a + b;
    }
}

Java OOP — Vorteile

  • Ausgereifte Vererbungshierarchie (abstract, sealed)
  • Default-Methoden in Interfaces
  • Reflection für Frameworks (Spring, Hibernate…)
  • Records (seit Java 16) für kompakte Datenklassen
  • 30 Jahre erprobte OOP-Patterns

Java OOP — Nachteile

  • Viel Boilerplate (getter/setter, Konstruktoren)
  • public/private/protected schwer zu überblicken
  • Kein fn vs. fnc — Unterschied statisch/instanz weniger klar
  • String-Konkatenation umständlich

λ Funktionales Programmieren

Lambdas & Funktionstypen

Java

// Funktionstypen via java.util.function.*
Function<Integer, Integer> doubled = n -> n * 2;

// Methoden-Referenz
Function<String, Integer> len = String::length;

// Higher-Order-Funktion
static int apply(int x, Function<Integer, Integer> f) {
    return f.apply(x);
}
apply(21, n -> n * 2); // 42

// Stream-API
List.of(1,2,3).stream()
    .map(n -> n * 2)
    .filter(n -> n > 2)
    .collect(Collectors.toList());

Tinox

// Funktionstyp als Parametertyp
fn apply(x: Int64, f: fnc(Int64) -> Int64) -> Int64
{
    return f(x);
}

// Lambda-Ausdruck
let doubled = apply(21, n => n * 2); // 42

// Lambda als Wert
let square: fnc(Int64) -> Int64 = fn(x: Int64) -> Int64
{
    return x * x;
};

// Kurzform
let add = (a, b) => a + b;

TypeScript

// Funktionstypen nativ
const doubled = (n: number) => n * 2;

// Methoden-Referenz via bind
const len = (s: string) => s.length;

// Higher-Order-Funktion
function apply(x: number, f: (n: number) => number) {
    return f(x);
}
apply(21, n => n * 2); // 42

// Array-API (kein Stream nötig)
[1, 2, 3]
    .map(n => n * 2)
    .filter(n => n > 2);

Pattern Matching

Java

// Java 21: Pattern Matching mit switch
Object obj = ...;
String result = switch (obj) {
    case Integer i -> "int: " + i;
    case String s  -> "str: " + s;
    default        -> "other";
};

// Enum switch (ohne Exhaustiveness-Garantie)
Direction d = Direction.NORTH;
switch (d) {
    case NORTH -> System.out.println("N");
    case SOUTH -> System.out.println("S");
    // default nötig oder Warning
}

Tinox

enum Direction
{
    North; South; East; West;
}

fnc turn(d: Direction) -> Direction
{
    match d
    {
        North => return East;
        East  => return South;
        South => return West;
        West  => return North;
    }
}

// Exhaustiveness wird geprüft

TypeScript

type Direction = "North"|"South"|"East"|"West";

function turn(d: Direction): Direction {
    switch (d) {
        case "North": return "East";
        case "East":  return "South";
        case "South": return "West";
        case "West":  return "North";
    }
}

// Discriminated Unions als Alternative:
type Shape =
    | { kind: "circle"; r: number }
    | { kind: "rect";   w: number; h: number };

Tinox Funktional — Vorteile

  • Funktionstypen direkt in der Sprache (kein java.util.function Import)
  • Kompakte Lambda-Syntax (n => n * 2)
  • match ist ein vollständiges Statement
  • Exhaustiveness-Check bei Enums

Tinox Funktional — Nachteile

  • Keine Stream-API (filter/map/reduce Pipelines)
  • Closures noch eingeschränkt (kein volles Capture)
  • Kein funktionales Typsystem (Haskell-Niveau)

⚡ Concurrency & Async

Java

// Klassischer Thread
Thread t = new Thread(() -> {
    System.out.println("Worker");
});
t.start();
t.join();

// CompletableFuture (Java 8+)
CompletableFuture<Integer> future =
    CompletableFuture.supplyAsync(() -> fetchData(21))
                     .thenApply(n -> n * 2);
int result = future.get(); // 42

// Virtual Threads (Java 21)
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> process());
}

// Channel: kein natives Konzept (BlockingQueue)
BlockingQueue<Integer> ch = new LinkedBlockingQueue<>();
ch.put(99);
int v = ch.take();

Tinox

async fn fetchData(id: Int64) -> Int64
{
    return id * 2;
}

fn main() -> Int64
{
    // Spawn + Await
    let handle = spawn fetchData(21);
    let result = await handle; // 42
    println(result);

    // Channels (Go-inspiriert)
    let ch = channel;
    send ch -> 99;
    let v = recv ch;
    println(v);

    return 0;
}

TypeScript

async function fetchData(id: number): Promise<number> {
    return id * 2;
}

async function main() {
    // Async/Await
    const result = await fetchData(21); // 42
    console.log(result);

    // Parallele Ausführung
    const [a, b] = await Promise.all([
        fetchData(1),
        fetchData(2),
    ]);

    // Kein nativer Channel (via MessageChannel)
}

Tinox Concurrency — Vorteile

  • async/await direkt in der Sprache (kein Framework nötig)
  • Channels als First-Class-Konzept (Go-ähnlich)
  • spawn ist intuitiver als CompletableFuture-Ketten
  • Kein Import aus java.util.concurrent

Tinox Concurrency — Nachteile

  • Kein ausgereiftes Thread-Pool-API wie Java Executors
  • Structured Concurrency (Java 21) fehlt noch
  • Weniger kampferprobt auf High-Concurrency-Workloads
  • Kein reaktives Ökosystem (RxJava, Project Reactor)

🚀 Memory Management & Performance

Java

// JVM-basiert: alles auf dem Heap
// GC-Pausen je nach Collector (G1, ZGC, Shenandoah)
// Warmup-Zeit (JIT-Kompilierung)

// Startup: ~100–500ms (JVM-Start)
// Peak-Performance: sehr hoch (JIT-optimiert)
// Memory-Overhead: JVM-Heap + MetaSpace
// Native Image möglich (GraalVM)

Tinox

// LLVM-Backend: AOT-kompiliert zu Maschinencode
// GC: eigene Tinox Runtime (C, pthread-basiert)
// Kein JVM-Warmup

// Startup: instant (native Binary)
// Peak-Performance: vergleichbar mit C
// Memory: kein JVM-Overhead
// Kein GraalVM nötig

TypeScript

// Transpiliert zu JavaScript → Node.js / V8
// GC: V8-Garbage-Collector (generational)

// Startup: schnell (~50–200ms Node.js-Start)
//           sehr schnell mit Bun
// Peak-Performance: gut für I/O-bound Workloads
// Memory: V8-Heap-Overhead
// Bun: native TS-Ausführung ohne tsc

Tinox — Performance-Vorteile

  • Kein JVM-Start-Overhead (instant startup)
  • LLVM-Optimierungen (O2/O3) direkt anwendbar
  • Kein Boxing/Unboxing bei Primitiven in Generics
  • Kein MetaSpace-Overhead
  • Ideal für CLI-Tools, Microservices, Embedded

Tinox — Performance-Nachteile

  • JVM-JIT erreicht nach Warmup oft sehr hohe Performance
  • Tinox GC noch nicht so ausgereift wie G1/ZGC
  • Kein Profiling-Tooling wie Java Flight Recorder
  • Kein GraalVM-nativer-Image als Fallback

Tinox Stdlib — Vorteile

  • JSON, HTTP-Server, JWT, bcrypt ohne externe Dependencies
  • REST-Framework in der Stdlib (Annotationsbasiert)
  • Cron, PubSub, Cache out-of-the-box
  • Stdlib in Tinox selbst geschrieben (kein Paradigmenwechsel)

Tinox Stdlib — Nachteile

  • 30 Jahre kleiner als das Java-Ökosystem (Maven Central)
  • Keine Datenbank-Treiber (JDBC-Äquivalent fehlt)
  • Kein Spring/Quarkus/Micronaut-Ökosystem
  • Kein zentrales Repository für Third-Party-Libraries (URL-basiert)

Tinox Tooling — Vorteile

  • Alles in einem CLI (build, run, check, fmt, install, package)
  • Kein Build-Tool-Konfigurationschaos (Maven XML, Gradle DSL)
  • Paket-Manager integriert: YAML-Manifest, URL-basierte Deps, kein zentrales Repo nötig
  • Native Binary = kein JRE-Deployment nötig
  • LSP + Eclipse-Plugin vorhanden
  • Formatter ist Bestandteil der Sprache

Tinox Tooling — Nachteile

  • Kein zentrales Package-Repository (URLs müssen bekannt sein)
  • Kein Debugger (GDB-Integration fehlt)
  • Kein IntelliJ/VS Code Plugin (nur Eclipse)
  • Kein REPL (geplant, noch nicht implementiert)

Tinox Paket-Manager — Vorteile

  • YAML statt XML — deutlich lesbarer und kompakter
  • Kein zentrales Repository nötig (URL-basiert, self-hosted möglich)
  • Alles im selben CLI (kein separates Tool wie mvn/gradle)
  • tinox package erzeugt direkt ein verteilbares tar.gz
  • Deps landen projekt-lokal (.tinox/deps/) — kein globaler Cache-Konflikt
  • Import-Resolver erkennt installierte Deps automatisch

Tinox Paket-Manager — Nachteile

  • Kein zentrales Repository wie Maven Central / npm
  • URLs müssen manuell bekannt sein (kein tinox search)
  • Kein Dependency-Version-Resolution (keine Konflikterkennung)
  • Keine transitive Dependency-Auflösung
  • Keine Checksums / Signaturverifikation (noch)

@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping
    public ResponseEntity<List<User>> listUsers() {
        return ResponseEntity.ok(userService.findAll());
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public User createUser(@RequestBody User user) {
        return userService.save(user);
    }

    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void deleteUser(@PathVariable Long id) {
        userService.delete(id);
    }
}

Tinox Web — Vorteile

  • Identische Annotation-Syntax wie Spring (leicht erlernbar)
  • HTTP-Server direkt in Stdlib — kein Framework-Download
  • Kein Spring-Kontext-Overhead, kein Application-Start
  • Native Binary startet instant (kein JVM-Warmup)
  • Path-Parameter, Middleware, Routing out-of-the-box

Tinox Web — Nachteile

  • Kein Spring Boot-Ökosystem (Security, Data, Actuator…)
  • Kein automatisches JSON-Serialization (ObjectMapper-Äquivalent)
  • Kein ORM / Datenbankanbindung
  • Weniger battle-tested bei Produktions-Workloads
  • Kein API-Dokumentationsgenerator (Swagger/OpenAPI)

🔒 Fehlerbehandlung & Null Safety

Java

// Checked vs. Unchecked Exceptions
public int divide(int a, int b) throws ArithmeticException {
    if (b == 0) throw new ArithmeticException("Division by zero");
    return a / b;
}

try {
    int r = divide(10, 0);
} catch (ArithmeticException e) {
    System.err.println("Fehler: " + e.getMessage());
} finally {
    cleanup();
}

// Null Safety: nicht vorhanden
String s = null;
s.length(); // NullPointerException!

// Optional als Workaround (Java 8+)
Optional<String> opt = Optional.ofNullable(s);
opt.ifPresent(System.out::println);

// Defer für automatisches Cleanup
fn readFile(path: String) -> String
{
    let f = open(path);
    defer { f.close(); }
    return f.read();
}

TypeScript

function divide(a: number, b: number): number {
    if (b === 0) throw new Error("Division by zero");
    return a / b;
}

try {
    const r = divide(10, 0);
} catch (e) {
    // e ist unknown — Typ-Guard nötig
    if (e instanceof Error)
        console.error(`Fehler: ${e.message}`);
} finally {
    cleanup();
}

// Kein defer — try/finally als Alternative
// Result-Pattern via neverthrow / fp-ts:
import { Result, ok, err } from "neverthrow";
function safeDiv(a: number, b: number)
    : Result<number, string> {
    return b === 0 ? err("Division by zero") : ok(a/b);
}

Tinox Fehlerbehandlung — Vorteile

  • defer ist eleganter als try-with-resources
  • Kein Checked-Exception-Chaos (keine throws-Deklarationen)
  • LIFO-Reihenfolge mehrerer defers ist intuitiv
  • Option<T> / Result<T> in Stdlib verfügbar

Tinox Fehlerbehandlung — Nachteile

  • Kein echtes Null-Safety-Typsystem (wie Kotlin/Rust)
  • Exception-Hierarchie weniger ausgefeilt als Java
  • Result<T> noch nicht als nativer Sprachkern integriert

🏆 Fazit & Empfehlung

Wann ist was die bessere Wahl?

Java verwenden, wenn…

du ein großes Team, ein riesiges Ökosystem (Spring, Hibernate, JEE), oder Unternehmens-Software mit langfristigem Support brauchst. Wenn Datenbankanbindung, Microservices-Orchestrierung (Kubernetes, Spring Cloud) oder ein breites Tooling (IntelliJ, Profiler, APM) entscheidend sind.

Tinox verwenden, wenn…

du native Performance ohne JVM-Overhead willst, kleine bis mittlere Services oder CLI-Tools baust, oder die Java-ähnliche Syntax mit weniger Boilerplate schätzt. Ideal für Eigenentwicklungen, Lernprojekte, und Szenarien wo instant startup wichtig ist.

TypeScript verwenden, wenn…

du Web-Apps, APIs oder Full-Stack-Projekte mit dem riesigen npm-Ökosystem baust. Wenn Frontend und Backend dieselbe Sprache teilen sollen, starke IDE-Unterstützung gefragt ist, oder das Team bereits JavaScript-Background hat.

Java gewinnt bei…

Ökosystem-Tiefe, Datenbankintegration, Enterprise-Patterns, Tooling-Reife (Debugger, Profiler, APM), Community-Größe, Zertifizierungen, und Langzeit-Support durch Oracle/OpenJDK.

Tinox gewinnt bei…

Startup-Zeit, nativer Performance, Syntax-Klarheit (let/var, String-Interpolation, Ranges), integrierten REST-Annotationen ohne Framework-Dependency, dem einheitlichen CLI (build/run/check/fmt/install/package) und dem schlanken YAML-basierten Paket-Manager.

TypeScript gewinnt bei…

Ökosystem-Breite (npm), Frontend/Backend-Sharing, strukturellem Typsystem (Discriminated Unions, Utility Types), exzellentem LSP (tsserver), Null Safety (strictNullChecks) und der größten Developer-Community nach Java.

Tinox ist eine moderne Sprache in aktiver Entwicklung — der Paket-Manager (tinox install/add/package) ist verfügbar, weitere Lücken (Debugger, REPL, zentrales Repository) werden in zukünftigen Versionen geschlossen.
